AI is genuinely useful in production software. It is also confidently wrong in ways that look like progress. The difference between the two outcomes is not the model. It is the review workflow around it.

I use AI for scaffolding, tests, refactors, migrations, documentation, and debugging. I do not let it merge code, invent customer facts, or decide that a database change is safe. Those are human responsibilities, and they stay human even when the first draft is generated.

Where AI earns its keep

  • Scaffolding: turning a clear interface description into a first-pass module, template, or test file.
  • Tests: proposing edge cases that a tired engineer might miss.
  • Refactors: applying a mechanical rename or extraction across a codebase, then letting tests verify it.
  • Migrations: drafting a schema change and the corresponding backfill, with a human reviewing the data assumptions.
  • Documentation: turning a working change into a readable explanation for the next person.
  • Review: summarizing a diff and flagging suspicious patterns before a human review.

The common thread is that these tasks have a clear correctness signal: tests pass, the diff is small, the behavior is observable. AI is most useful when the feedback loop is fast and the blast radius is contained.

Where it becomes dangerous

Hallucinated APIs and dependencies

Generated code can reference a function that does not exist, a library version that was never released, or a configuration option that changed two years ago. It looks plausible because it is syntactically fluent.

Run the code. Install the dependency in a clean environment. Read the actual documentation for the version you are using. “It compiles in the model’s imagination” is not verification.

Insecure defaults

AI-generated code often reproduces the most common pattern, not the safest one. That can mean missing authorization checks, permissive CORS, secrets in logs, or string-built SQL.

Security review is not optional because the code was generated. If anything, generated code deserves a closer look at the boundaries: authentication, authorization, input validation, file handling, and outbound requests.

Invented facts and metrics

This is especially relevant on a portfolio or marketing site. A model can produce a polished case study with numbers that were never measured. That is not a content shortcut; it is a credibility risk.

Use AI to improve the shape of a sentence, not to source a claim. Every metric, client name, and testimonial needs a real origin and a human who can defend it.

Migrations that “should be fine”

Schema changes are where confident guesses become outages. A generated migration may lock a large table, drop a column that still has readers, or backfill data with the wrong assumption about nulls.

Review migrations separately from application code. Test them against a copy of realistic data. Have a rollback plan. If the change is destructive, slow down.

A review-first workflow

The workflow that works for me is deliberately boring:

  1. Write the acceptance criteria first. What observable behavior should be true when this is done?
  2. Write or identify the tests. If the change cannot be tested, explain why before generating code.
  3. Generate a small draft. Keep the diff narrow enough to review in one sitting.
  4. Run the tests, linters, and type checks. Fix the failures before asking a human to look.
  5. Review the diff as if a junior engineer wrote it. Check assumptions, error paths, and security boundaries.
  6. Deploy to staging. Exercise the real user flow, not just the happy-path unit test.
  7. Ship with a rollback path. Know how to revert before you need to.

The order matters. Generating first and inventing acceptance criteria afterward is how teams end up with code that is impressive and wrong.

Practical rule: if you cannot explain the change without referring to the prompt, you are not ready to deploy it.

Keep humans accountable

A pull request should have a named human owner whether or not AI helped write it. That person is responsible for the behavior in production, the tests, and the rollback. “The model suggested it” is not an incident response.

Teams should also be clear about data handling. Do not paste customer data, credentials, or private source code into a tool that retains it without an approved agreement. Prompt hygiene is part of security hygiene.

AI changes the speed, not the standard

The useful promise of AI is not that we stop reviewing code. It is that we spend less time typing boilerplate and more time thinking about boundaries, failure modes, and the user’s actual problem.

That is a good trade. It only works if the review bar stays where it was — or goes higher.
